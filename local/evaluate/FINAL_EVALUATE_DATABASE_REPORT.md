## 5. Scoring model

The currently implemented policies are `REGULAR_V3` and `TRAINING_V2`; this work did not replace them with older candidate weights. The official score and Tier come from the latest valid CLOSED round aggregate. OPEN aggregates and personal evaluator scores stay separate. Round close is transactional and freezes eligible accounts, aggregate, policy, score and snapshots. 39 legacy CLOSED rounds have null persisted aggregate fields and use the existing CLOSED-only fallback when their historical submissions can supply a score; their history was not rewritten.

## 6. Position and skill model

Account role, formal Evaluate store position, individual skill status and Roster shift role are separate concepts. Formal positions are explicit `store_job_definitions`/`employee_job_assignments` and may be multiple per employee; the current definitions cover only `full-role` and `trainer`. Back-of-house, water-bar and front-of-house are skill categories today, not proven formal qualifications.

A real isolated-browser submission reproduced a P1 bug: an evaluator's OPEN-round skill judgment immediately overwrote `employee_skills`. The unconditional write was removed. Conflicting personal judgments now remain in their own snapshots, while official current skills stay unchanged through submit and ADMIN close. An ADMIN can explicitly confirm an official skill from employee detail; the protected API validates progressive/binary status and rejects stale writes. Unknown remains distinct from NotTrained/CannotDo. No unapproved consensus algorithm was introduced.

## 7. Shared architecture

Evaluate's authenticated integration DTO version `1.4.0` contains canonical ID, current store/status/type, latest CLOSED score/Tier, explicit active same-store positions and current skill summary without unnecessary PII. List reads support bounded server pagination. Evaluate computes an active-workforce `workforceRevision` under repeatable read; Roster checks it across pages and after the final page, rejects duplicate IDs or revision drift, forwards the caller's existing session and reads fresh Evaluate data per request. This does not make a Roster write atomic with a later Evaluate change. Roster does not write scores, positions or skills. Published Roster JSON freezes the employee/shift/store/score facts it displays; future historical qualification displays would require a new publish-time snapshot. See the [integration contract](docs/ROSTER_INTEGRATION_CONTRACT.md).

A subsequent audit found that Roster could still save arbitrary required skill codes on a new ShiftRole. Evaluate now exposes a protected, PII-free active skill catalog, and Roster checks nonempty requirements before creating or activating a role. Unknown/inactive codes return 400; catalog failure returns 503 without writing. A read-only service call against the development database returned 13 active codes, including the corrected front and water-bar requirements.

A separate publish-path audit reproduced that an existing draft could be published after an assigned employee was archived or transferred. The route now fetches current Evaluate workforce, and Roster verifies every assignment inside its publication transaction. New revision JSON freezes the current name/type/CLOSED score/Tier; prior revisions remain immutable. A failed current-workforce read also blocks publication. The two databases cannot share an atomic transaction, so an Evaluate change immediately after the read remains a narrow race.

The same lifecycle audit found that draft shift movement and resizing still bypassed the active-workforce check. An API test reproduced a successful move while Evaluate was unavailable. The reposition route now refreshes the workforce and the service rejects a saved assignment missing from the current store list. Real PostgreSQL testing confirmed an ineligible move leaves the shift time and version unchanged.
