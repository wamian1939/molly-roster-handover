## Store archive and employee lifecycle race audit, 2026-10-09

Fresh migrated PostgreSQL fixtures reproduced four write races before correction: creating an employee after its store was archived between the preflight read and insert; transferring or restoring an employee into a store archived after preflight; and promoting a TRAINING employee after either the employee or their store was archived. Employee create, transfer, restore and promotion now lock and recheck the target store row inside the write transaction. Promotion and restore additionally use the employee `updatedAt` version and status in a conditional update. A concurrent duplicate explicit employee ID previously surfaced raw Prisma `P2002` (HTTP 500); the service now maps that verified ID conflict to HTTP 409. The fresh-schema database suite covers each race and checks the remaining canonical ID, status and position rows. No schema change, data backfill or development employee write was required.

## Employee concurrent write follow-up, 2026-10-09

The employee update path previously read a row before its transaction and then updated by ID only. Two administrators could therefore both save a version they had read earlier, with the later write silently replacing the first. The update now uses `employees.updatedAt` as an optimistic version with a conditional `updateMany` inside the existing transaction. A stale version returns 409; a position delete preceding the conditional update rolls back with the transaction. No schema migration or existing employee row edit was required. A fresh isolated PostgreSQL test issued two updates against one version and verified one success, one 409 and a remaining position in the employee's current store. Lifecycle endpoints are distinct write flows and should be included in a later whole-employee version audit.

## Constraints and findings

`employees.id` is the primary key; employee/store FK restricts deletion. Evaluations and rounds restrict employee deletion. Current skills are unique on `(employeeId, skillDefinitionId)` and assignments on `(employeeId, jobId)`. `employees_archive_state_check` requires status and archive timestamp to agree. Evaluation round/evaluation scope uses a composite FK; existing CLOSED history freeze triggers remain. Roster has no Employee table and its historical publication JSON is owned by Roster.

**Fixed:** Employee job assignments previously had separate employee and job FKs, allowing a direct SQL write to associate an employee with a different store's job. Migration `20261008130000_enforce_employee_job_store_scope` adds `storeId`, backfills it from employees, checks for conflicts, and adds composite FKs to employee and job with supporting unique indexes. The preflight conflict count was zero. The service now supplies the canonical store ID for create and transfer writes. The migration was tested from empty schema and against a restored copy of all current development data before applying to the local development database. Cross-store insert failed in a rollback-only transaction in the restored copy. Prisma status showed 33 migrations at that point; 34 are now applied after the archive-state migration.

**Fixed in the separate Roster integration:** Roster's account DTO still read the removed single `storeId` field, while Evaluate now issues `storeIds`. This made evaluator access fail or remain single-store. Roster authorization now checks membership in the actual `storeIds` array and offers a selector to authorized multi-store evaluators. Backend 403/200 and frontend selection tests cover the boundary.

**Fixed in Roster's local database:** global front/water-bar ShiftRoles referenced five obsolete skill codes that did not exist in Evaluate. As a result, skill-qualified employees were incorrectly shown as missing those role requirements. A conditional Roster migration replaced only untouched default arrays with canonical Evaluate codes; the seed no longer overwrites configured roles. An isolated-schema existing-row migration test and a real cross-database check confirmed front, water and back roles have no missing required codes for an appropriately qualified current employee. Roster's four published snapshot JSON records retained the same hash.

**Fixed after a real browser/DB reproduction:** an OPEN-round evaluator submission still upserted every submitted skill into `employee_skills`. In an isolated schema, evaluator A changed `tea-preparation` from Independent to Proficient before ADMIN close, while the official score remained null. The submission write was removed. Individual judgments now remain only in evaluation skill snapshots; ADMIN close does not guess a consensus skill status. An explicit ADMIN current-skill confirmation endpoint checks skill mode and the expected update timestamp. Isolated PostgreSQL tests cover conflicting evaluators, unchanged current skill on submit/close, immutable CLOSED snapshots, stale writes and concurrent confirmations. Browser and Roster API checks showed an explicit ADMIN confirmation propagating without changing the CLOSED score.

**Fixed historical-detail data mixing:** `roundAggregateInclude` previously joined current `EmployeeSkill` into each Round and the DTO spread that mutable relation into `employee`, including CLOSED history. A new unit test reproduced the field leak before the fix. Round reads now select only employee ID/name and the DTO explicitly emits only those fields; historical category scores continue to come from frozen evaluation skill snapshots. An isolated PostgreSQL test confirmed that changing current skill after close does not add it to CLOSED detail and does not alter stored snapshots. Full DB-enabled backend suite passed 163/163 and a hash-matched isolated backend production build passed. No database migration or historical data rewrite was needed.

**Fixed history API privacy leak:** `GET /api/evaluation-rounds/history` previously returned ADMIN personal score/name fields to STORE_EVALUATOR because its service received only store scope, not actor role. A pre-fix test reproduced the leak. The route now passes AuthContext; the service queries ADMIN personal evaluations only for ADMIN on the visible page and omits both fields entirely for evaluator responses. An isolated PostgreSQL case and a real authenticated HTTP comparison with disposable ADMIN/evaluator accounts verified the boundary. Full DB-enabled backend suite passed 164/164. No database row or scoring rule changed.

**Fixed lifecycle concurrency gap:** Employee transfer/archive checked for an OPEN round outside the write transaction. A new round could appear between that check and the employee mutation. Transfer/archive now take the same transaction advisory lock as round creation and check for OPEN under the lock. Round creation reads the current committed employee after locking. An isolated migrated PostgreSQL schema exercised ten concurrent transfer/archive and create cases, with no archived or transferred employee left with an OPEN round in the old store. This required no schema migration or development employee edit.

**Fixed transferred-score gap:** the integration, current-store roster, skill board and current analytics queried CLOSED rounds by the employee's present store ID. A transferred employee with a valid former-store CLOSED round therefore appeared to have no official score. An isolated PostgreSQL test reproduced `77.5/T2` becoming null after transfer. Current employees are still selected by authorized store, but their latest CLOSED aggregate is now selected by canonical employee ID across stores. The employee-detail response adds a minimal official score summary while prior-store personal history remains access scoped. No historical round or development employee row was altered.

**Clarified empty CLOSED round behavior:** an isolated PostgreSQL test closed a later round without an aggregate after an earlier 77.5/T2 result. The project's `PRODUCT.md` specifies the latest *valid* round aggregate as current, so the existing readers correctly retain the earlier result while both CLOSED rounds remain in history. A provisional change that cleared the score was reverted after this contract check. The expected behavior is covered by an isolated DB regression while a business clarification request is pending. A read-only development query found no latest empty CLOSED round among 25 employees with 40 CLOSED rounds; no development employee score was changed.

39 old CLOSED rounds have null persisted `finalAggregateOverall`; these predate the snapshot fields. Current read service applies its legacy CLOSED-round aggregate fallback. They were not rewritten. A September store-job migration has one rolled-back failed attempt followed by a successful applied attempt; Prisma status reports current schema up to date. Treat these as migration-history facts, not active failures.
