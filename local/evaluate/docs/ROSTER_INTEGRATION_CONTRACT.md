# Roster integration contract 1.4.0

Evaluate serializes employee creation, store transfer and restoration against store archival by locking the target store row inside its write transaction. Roster continues to receive current active-store workforce from the protected read API; it does not resolve these races or write employee status itself. An archived store or a conflicting employee version yields a 409 on the Evaluate write path, and no new current workforce row is published by that rejected write.

Evaluate is the sole writer for employees, stores, formal positions, current skills and CLOSED-round official scores. Roster is the sole writer for availability, shifts, shift roles, assignments and publications. The projects keep separate PostgreSQL databases and Prisma migration owners.

## Authenticated read API

The Roster adapter checks canonical identity at the response boundary. Evaluate's `employee: null` detail response becomes Roster HTTP 404; a returned ID that differs from the requested ID, or a store workforce row whose `storeId` differs from the requested store, becomes HTTP 503 and cannot enter a roster write. This is defensive validation of the protected Evaluate contract, not a second employee authority.

Evaluate scopes employee detail to the caller's **current** authorized store. On transfer, the former store loses the employee from both current workforce and scoped detail; the destination store receives the same canonical ID and latest valid CLOSED official score. On archive, active workforce omits the employee, while authorized detail returns `isActive: false` and retains CLOSED score/history linkage. Roster keeps older publication revisions from its frozen snapshots. An isolated PostgreSQL regression verifies the transfer/archive read boundary; it does not grant former-store users access to current employee data.

All endpoints require an Evaluate session cookie; Roster forwards the caller cookie server to server and enforces the same store scope. STORE_EVALUATOR can access only IDs in Evaluate's current `storeIds` account claim, including multi-store access. Roster checks the contract's major version and responds 503 if incompatible or upstream unavailable. No service credential is exposed to the browser.
Roster forwards only `evaluate_molly_session` from the browser Cookie header; unrelated cookies never enter Evaluate requests.

Roster proxies browser login/logout through its own backend. Its upstream POST requests set `Origin` to Evaluate's configured site origin so Evaluate's production CSRF check accepts them. The default is the origin of `EVALUATE_API_BASE_URL`; if that address is internal and differs from Evaluate `APP_ORIGIN`, configure `EVALUATE_APP_ORIGIN` explicitly in Roster. Roster never uses an arbitrary browser-supplied Origin for this upstream request.

Login attempts are reserved in Evaluate's PostgreSQL `login_rate_limits` table by a hash of the IP visible to Evaluate and normalized username. Ten attempts are allowed per 15-minute window across Evaluate instances; further attempts return HTTP 429 and a numeric `Retry-After` header. For proxied Roster login, the visible IP can be Roster's upstream address, so users of the same account share that bucket. Roster relays the header and creates no session on failure; successful authentication clears that key. Do not trust an arbitrary browser-supplied forwarded IP to split the bucket. The limit is an authentication control, not employee or roster master data; deploy the Evaluate migration before loading the new backend. Target edge abuse controls and HTTPS proxy acceptance remain release checks.

Local production-mode network acceptance on temporary 4010/4035 alternated ten invalid logins between Evaluate and Roster, then received 429 through Roster with `Retry-After: 900` and no session cookie. A different disposable STORE_EVALUATOR account logged in through Roster and passed `/auth/me`. The freshly migrated test schema, generated credentials and temporary services were removed. This proves the paired local proxy behavior; deployed HTTPS and load-balancer address semantics remain unverified.

| Evaluate endpoint | Response |
|---|---|
| `GET /api/roster-integration/contract-version` | version and generation time |
| `GET /api/roster-integration/stores` | active stores in scope |
| `GET /api/roster-integration/skill-definitions` | active skill code, display name, category and mode; requires Evaluate session |
| `GET /api/roster-integration/stores/:storeId/employees` | active current employees in scope; optional `page` and `pageSize` (maximum 100) |
| `GET /api/roster-integration/employees/:employeeId` | one current or archived employee in scope |

Roster exposes corresponding read-only `/api/workforce/*` endpoints. The employee response includes `id`, `displayName`, `employeeType`, `employmentType`, `storeId`, `storeName`, `isActive`, `officialScore`, `positions`, and `skillSummary`. `officialScore` is `{score,tier,roundId,closedAt}` or null. `positions` contains explicitly assigned active same-store job `{id,code,name}` records; an empty array is unknown/unassigned, not an inferred lack of competence. `skillSummary` has category percentages, qualified skill codes, detailed skill statuses, and distinct binary operation statuses. No bank, tax, contact, birth, address, visa, evaluator or review text fields are selected.

The store filter authorizes which **current employees** can be read. For an authorized employee, `officialScore` follows the canonical ID and comes from the newest valid CLOSED round across prior stores. A transfer preserves the official score while a destination round is OPEN. Under the present PRODUCT.md rule, a later CLOSED round without a scored aggregate does not replace the prior valid official score; both rounds remain in history. Historical evaluator identities, personal submissions and review text remain scoped to their original store; the employee-detail API exposes a separate minimal `officialScore` summary for this case.

Roster exposes `GET /api/workforce/skill-definitions` to its authenticated settings page. It forwards the Evaluate session to the protected catalog and returns only active code/name/category/mode fields. The settings picker displays names and exact codes grouped by category; the backend remains authoritative when a role is saved.

No implicit caching is used in the current adapter: each workforce read checks Evaluate. Both services set `Cache-Control: no-store, private` on all `/api` responses, including authenticated workforce reads. A 401 redirects to sign-in; 403 is store isolation; 404 is missing employee; 503 prevents assignment operations when upstream fails. Roster requests pages of 100, joins and validates the complete workforce before returning a flattened response without upstream page metadata, rejects duplicate IDs, changing contract versions or pagination modes, changed totals across pages, and incomplete final results; one load is capped at 100 pages (10,000 employees). A changing workforce is retried rather than used for assignments or publication. Unpaged 1.x clients remain compatible. The endpoint is versioned by response metadata; a future incompatible shape requires a new major version.

Version 1.4.0 adds `workforceRevision` to paginated store employee responses. Evaluate computes it from the complete active employee identity/membership set in the same repeatable-read transaction as each page. Roster requires the revision to match on every page and checks it once more after the final page. A rename or same-count transfer during pagination therefore yields 503 instead of a mixed list. The revision covers employee identity, name, type, employment type and update timestamp; current skill, formal position and CLOSED score changes across separate page requests are refreshed on the next read. Evaluate and Roster still do not share a transaction, so a change after the final check remains a cross-service race. Unpaged 1.x clients and earlier 1.3.x paginated responses remain readable.

Local paired acceptance can be reproduced without changing the normal services: `backend/scripts/browser-acceptance-environment.ts prepare` creates a disposable Evaluate schema, `backend/scripts/seed-workforce-revision-acceptance.ts` adds 91 fixture employees for 101 total, and `scripts/start-browser-acceptance.ps1 -BackendOnly` starts the candidate Evaluate API on 4010. With the confirmed local Roster development `DATABASE_URL` set, run Roster's `backend/scripts/verify-workforce-revision-http.ts`. It sends HTTP requests into the candidate Roster app through Supertest, proxies a generated evaluator session to the temporary Evaluate API, checks Roster database/Evaluate health, reads two pages and confirms the final revision recheck. Stop the exact temporary Evaluate process and run Evaluate's browser acceptance `cleanup` command afterward. These scripts reject nonlocal database targets or missing disposable state; neither step deploys to production.

Roster Staff refreshes the workforce on store change, page focus or visibility, every 60 seconds while visible, and manual request. Successful reads replace current employee names, store membership, formal positions, skills and official scores by canonical ID while preserving the selected availability week and draft. The page shows the latest successful fetch time; a failed refresh labels the list stale and disables availability submission until a successful read. The Roster backend still checks active current-store membership at write time. Published revisions continue to use frozen publication snapshots.

On a successful Calendar refresh, editable DRAFT shift cards and the grouped-shift picker use the current active Evaluate name by canonical Employee ID for display. This does not rewrite Roster's saved assignment snapshot. PUBLISHED Calendar periods and publication history continue to show their frozen names; absent or inactive employees fall back to the saved name and remain subject to the existing eligibility warning.

The Calendar staff picker now labels its ShiftRole filter as a check against required skill codes. Each employee row separately shows Evaluate's explicit formal positions or `未确认` when none is assigned; meeting skill requirements is never described as proof of formal position qualification. This is decision support only and does not write Evaluate positions.

Roster validates active membership in the current store before a new assignment and again immediately before a draft is published. A missing, archived or transferred employee blocks publication with `ARCHIVED_EMPLOYEE` and preserves the draft and earlier revisions. Rename, transfer, archive, closed score and position changes become visible on the next read. Each new publication revision freezes the current Evaluate name/type and latest CLOSED score/Tier at publication time; earlier revisions remain unchanged. A ShiftRole and skill match are scheduling hints; neither writes Evaluate positions.

Roster also refreshes the Evaluate workforce before moving or resizing a saved draft shift. If any saved assignment is no longer active in that store, the move returns `ARCHIVED_EMPLOYEE` without changing the shift; an Evaluate outage returns 503. Copy, repeat, create and edit paths already use the same active-store boundary. Exporting a clearly labelled draft remains a planning operation; publication still requires the current employee check.

Generic batch shift updates also refresh active workforce and check every saved assignee inside the Roster transaction. An archived/transferred employee or Evaluate outage blocks the entire batch before any shift is changed. Draft deletion remains available for cleanup.

Availability replacement also requires the employee to be active in the requested current store. An archived or transferred employee receives `ARCHIVED_EMPLOYEE`; an Evaluate outage returns 503 before any availability write. Earlier availability records remain in Roster for history.

Publication snapshots also retain their own store, period, shift times, role name/color and assignment IDs. Formal positions and detailed skills are currently decision-support inputs and are not displayed as historical publication facts, so they are not frozen in the publication JSON. Any future historical qualification display must first add a publish-time snapshot; it must never join a past publication to today's mutable skills or positions and present them as past facts.

Current skill changes also become visible on the next read, but only after an explicit Evaluate ADMIN confirmation. A single evaluator's OPEN-round skill judgment and ADMIN close do not overwrite `employee_skills`. In isolated browser acceptance, conflicting Proficient/NotTrained submissions left the official skill Independent; explicit ADMIN confirmation to Proficient then appeared in Roster while the CLOSED score stayed 73.15/T2.

Evaluate's per-skill `current-skills/:skillDefinitionId/confirmations` history is an internal ADMIN audit surface. Roster receives the confirmed current skill state through the versioned integration DTO and has no access to approval reasons or approving-account details.

The publish guard is a fresh cross-service read followed by a Roster database transaction. Separate databases cannot provide one atomic lock over an Evaluate transfer/archive and a Roster publication; a concurrent change immediately after the read remains a narrow race. Publication history is immutable once committed, and the read must succeed or publication is refused.

Roster's built-in `front`, `water-bar` and `back-kitchen` ShiftRole requirements reference Evaluate `SkillDefinition.code`, not display names. The local audit found obsolete front/water-bar codes in Roster defaults; Roster migration `20261008140000_align_default_shift_role_skill_codes` corrects only untouched global defaults. This restores skill-based role matching, but matching a ShiftRole still does not grant a formal Evaluate position.

Before saving a ShiftRole with required skills, Roster reads the protected active skill catalog and rejects codes absent from it with HTTP 400. An unavailable or incompatible catalog yields HTTP 503 and no role write. This prevents new invalid requirements; existing custom requirements were not silently rewritten. Disabling an existing role does not require the catalog.
