## 1. Executive summary

Molly Roster is implemented as a separate, runnable scheduling product. It supports Month/Week/Day scheduling, drag creation, multi-employee shifts, availability, templates, batch operations, publication, summaries, employee-safe/admin exports, responsive use and shared Evaluate Molly authentication/workforce data. The 2026-10-09 browser audit found and fixed a P0 empty-cell click defect. A controlled internal pilot still requires the current candidate's full real-browser mutation and evaluator acceptance gates; it is not yet accepted.

## 2. Architecture

The frontend is React 19, TypeScript, Vite, Tailwind and FullCalendar. The API is Express 5 with Prisma 6 and an isolated PostgreSQL database. Frontend routes are lazy-loaded. Evaluate is accessed only over versioned HTTP integration APIs; no source import or shared database exists.

## 3. Evaluate integration

Evaluate exposes minimal contract-version, store, store-employee and single-employee endpoints. The DTO includes roster-safe identity, employment classification, active state, latest CLOSED-round official score/Tier and current skill summaries. Roster validates a major-version-1 contract and applies a strict Zod allowlist, so extra HR fields are discarded.

## 4. Authentication

Login, logout and `/auth/me` are proxied to Evaluate. The HttpOnly cookie is forwarded server-to-server. The client does not store session, role or store authority in localStorage. ADMIN may choose stores; STORE_EVALUATOR scope comes from the verified session.

## 5. Database

Roster owns only `RosterPeriod`, `Shift`, `ShiftAssignment`, `ShiftRole`, `EmployeeAvailability`, shift/availability templates, `RosterPublication` and store settings. Two formal migrations include relations, indexes and database checks. No Employee, UserAccount, Session or Evaluation authority is duplicated.

## 6. Calendar

The primary page provides shared store context, previous/today/next controls, refresh, view selection, drag selection, compact events, summary and warnings. Loading, empty and recoverable error states are present.

## 7. Month

Month uses compact role-colored events and FullCalendar overflow handling. Multi-employee names remain a single concise chip.

## 8. Week

Week provides high-density time-grid scheduling with overlapping columns, click edit, pointer create, drag move and resize.

## 9. Day drag selection

A real pointer 09:00→10:00 selection opened the dialog with exact prefilled values. Cancel made no write. Save persisted the shift and refreshed totals.

## 10. Shift modal

The accessible portal dialog has focus trapping, Escape/backdrop close, labeled inputs, role/time/break/template/notes, inline validation, sticky controls, save feedback and guarded two-step deletion.

## 11. Employee picker

Cards show name, employee type, score/Tier, category skill percentages, weekly hours, availability and role warnings. Search and type/Tier filters are present. The initial list renders 60 at a time; a 500-employee component test proves bounded rendering and later-item search.

## 12. Score/Tier integration

The current card score is the latest valid CLOSED `EvaluationRound` aggregate, never an individual evaluation or OPEN aggregate. The backend re-fetches current employees at write time and saves score, Tier, round id and closed time into each assignment snapshot.

## 13. Skill integration

Current Evaluate employee skills are summarized into back-of-house, water-bar, front-of-house and operations capability. Role requirements create visible warnings only; they never modify score/Tier and do not silently block an authorized manager choice.

## 14. Availability

The Staff page manages weekly or fortnightly dated availability, quick patterns and saved templates. AVAILABLE windows, UNAVAILABLE and UNKNOWN remain distinct. The picker reports outside-window, unavailable and unknown conditions explicitly.

## 15. Templates

Store-scoped shift templates configure time, break and optional role. Store-scoped availability templates carry 7–14 day slots and can be enabled/disabled with optimistic versions.

## 16. Batch operations

Managers can multi-select shifts for versioned role updates or deletion. Copy shifts transactionally offsets a week/fortnight, blocks overlapping target periods and refuses archived/cross-store employees.

## 17. Publish

Publish rejects empty/unassigned/stale periods, atomically increments the version and records an immutable JSON snapshot. Published events are read-only until an explicit reopen. Two real publication versions were verified in PostgreSQL.

## 18. Export

CSV and printable HTML are generated on the server. Employee output omits internal notes, scores and Tier; ADMIN manager output includes roster-time snapshots. CSV cells neutralize formula prefixes and HTML output escapes markup.

## 19. Staff page

The employee directory is read-only and sourced live from Evaluate. Roster adds scheduling hours and availability only; it does not expose edit controls or HR PII.

## 20. Settings

Store rules include timezone, operating hours, slot size, cycle, week start, minimum shift, default break and hour warnings. These values now drive the calendar/dialog; minimum duration and same-day operating bounds are also enforced server-side. Daily and configured-week totals remain separate in fortnight rosters. System roles are immutable; store roles are configurable and versioned.

## 21. Responsive

Desktop uses a floating branded shell and mobile uses a bottom navigation. The complete create flow passed at a real 390×844 CSS viewport with no body overflow and an in-bounds dialog.

## 22. Accessibility

Landmarks, labels, semantic buttons/links, visible focus, keyboard dialog containment, Escape behavior, 44px touch targets, status/alert roles and reduced-motion CSS are included. Destructive single and batch deletion both require an explicit second step.

## 23. Performance

Calendar does not render employee cards until needed. The picker paginates at 60 and filters with memoization. API queries use bounded includes and indexed period/store/date keys. Route-level lazy loading keeps Calendar outside the initial page chunk.
