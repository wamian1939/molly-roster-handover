# Scheduling Engine Lab

Independent Hurstville real-data scheduling Lab for Molly Roster. Its current UI and public API only expose Hurstville; synthetic stores remain isolated to automated tests. It does not modify the existing Calendar, publishing flow, or formal shift write API.

Current rules consist of shared shift-pattern definitions and seven independent weekday maps of pattern counts. New rule JSON and saved versions omit operating hours, opening headcount, time-slot staffing demand, date overrides, rule validity dates and numeric work/rest limits. Current solves target the pattern counts while retaining availability, qualification, supplied leave, non-overlap and each pattern's break duration. The weekly calendar stacks seven days vertically with time running downward. Historical versions remain readable. [Current contract and real-week check](docs/pattern-count-only-2026-10-27.md) supersedes older rule descriptions below where they conflict.

## Run on Windows

From this directory:

```powershell
.\scripts\test-lab.ps1
.\scripts\start-lab.ps1
```

Open <http://127.0.0.1:4188/>. Stop with `.\scripts\stop-lab.ps1`.

On Windows the isolated Python launcher may spawn a child interpreter that owns port 4188. The stop script verifies the recorded launcher path, stops its matching Lab server child first, then checks that the loopback port is closed before clearing the PID file. The start script refuses a port already in use so an old server cannot masquerade as a successful restart.

The test script creates `.venv-isolated`, installs pinned Python dependencies, runs the scenario tests, installs UI dependencies and builds the React UI. On this Windows host OR-Tools 9.14 and 9.15 crash inside the native `solve()` call, even with a one-variable model; 9.12.4544 passed the same smoke test and the Lab tests, so it is pinned. The standalone server binds to loopback only. Do not expose port 4188 to a network.

CLI example (mock data):

```powershell
.\.venv-isolated\Scripts\python.exe -m engine.cli --date 2026-10-26 --output .data\example.json
```

The CLI also accepts `--rules`, `--snapshot`, `--end-date`, and `--mode BEST_EFFORT`. New CLI runs accept only seven-day shift-pattern count rules. `STRICT` requires every day's count; `BEST_EFFORT` returns the candidate with explicit date-and-pattern gaps. Qualification, availability, leave, non-overlap and the break duration defined by a pattern remain constraints.

With `--output`, the terminal summary reports `pattern_gaps` and validation errors. The older slot fields remain in the output for historical result readers and are zero for new runs. Exit code 0 means a feasible result with no pattern gap, 3 means a feasible BEST_EFFORT result with a pattern gap, and 2 means no feasible result or a failed independent validation. A zero exit code is a technical CLI result, not business approval of a real roster; check `acceptance_gate` and the saved diagnostics before use.

Real-store rule saves reject a shift pattern whose role ID is absent from the current active Evaluate formal jobs. Each weekday must explicitly contain a nonnegative count for every defined pattern. Opening headcount, time-slot demand, date-specific staffing overrides and numeric work/rest limits are rejected on new saves. Invalid rules do not create a Lab version.

Rule saving validates the current weekday cycle, validity boundaries and timezone offset-change dates within a declared validity period. For an unrestricted rule it checks offset changes in the coming 400 days; each solve recompiles every requested day. This catches invalid local clocks on a future daylight-saving transition before the Lab creates a rule version without treating a saved rule as permanent legal approval.

## Architecture

| Directory | Responsibility |
|---|---|
| `engine/models.py` | Typed snapshot, rules, candidates and result contracts |
| `configs/global-base.json`, `engine/global_base.py` | Versioned Lab-wide seed for new store drafts; saved store rules keep their expanded values |
| `engine/config.py` | Validate weekday pattern counts and shift definitions; compile legacy demand rules for historical runs |
| `engine/candidates.py` | Generate complete legal shifts and possible break intervals for each qualified, available employee |
| `engine/solver.py` | CP-SAT choice of full shifts and break intervals, weekday pattern-count targets and soft objectives |
| `engine/validation.py` | Independent replay of complete-shift, break, coverage and employee constraints |
| `adapters/real.py` | Authenticated Evaluate API and repeatable-read, read-only Roster PostgreSQL snapshot |
| `api/` | Local FastAPI interface; rule versions and runs in isolated SQLite |
| `lab-ui/` | Separate React Rules and Calendar pages |
| `tests/` | Scenarios and API isolation tests |

The rule hierarchy starts with `configs/global-base.json` for slot size and optimization settings. A new store draft copies those values and records `global_base_version`. `base_day` supplies complete shift definitions; `weekly` records the minimum count of each pattern independently for Monday through Sunday. The seven maps are the only staffing targets for new saves and runs. Historical versions remain readable without rewriting them. To change the global seed for future drafts, edit the JSON and increment its `version`; previously saved store versions and historical runs do not change. The shipped seed is a Lab example, **not** a certified employment policy or Hurstville demand. A REAL/EXPLORATORY solve may test the engine with real read-only source data. Results are never eligible for reviewed acceptance or formal publishing. Neither path writes formal shifts.

Rules are versioned per store in `.data/lab.sqlite3`; runs record the engine version, rules version, source snapshot version, parameters, objective, assignments, breaks, per-slot effective headcount and diagnostics. `.data`, `.env`, Python environments and UI build dependencies are Git ignored. The Lab database may contain employee names and locally modeled hourly costs; keep it local and protected.

## Real data

For real Roster reads, configure `ROSTER_DATABASE_READONLY_URL` with a dedicated SELECT-only PostgreSQL account. The adapter requires this URL and refuses to use the backend `ROSTER_DATABASE_URL`. It also starts a database session with `default_transaction_read_only=on` and uses explicit read-only transactions. The current local Lab uses a dedicated role limited to seven required Roster tables; see [the local connection audit](docs/roster-readonly-connection.md).

The real source snapshot version hashes the requested store and local date range, the explicitly resolved store timezone, scheduling-relevant Evaluate employee fields (formal positions, skills, opening qualification, score and identity), active job definitions and Roster role, availability and shift rows. Row order alone does not change the version. The Evaluate workforce revision is retained separately in the version string; it does not cover every scheduling input by itself. Including the request scope changes source version strings across this Lab build even when the underlying rows have not changed; a preview for one date range cannot serve as the version for another. The historical rule version and real run parameter `timezone_source` record whether the timezone came from Roster or an operator-confirmed Lab rule.

Real solves append a separate fingerprint for manually reviewed approved-leave intervals to the source version. Equivalent UTC instants produce the same fingerprint regardless of input offset or interval order. An empty reviewed list still records that the leave check was supplied; it does not imply an authoritative leave feed exists.

Current real runs record `approved_leave_review` and `approved_leave_intervals`. Historical runs may contain older work, break or staffing confirmation parameters; the current pattern-count rules do not use them.

Open the Lab in the same browser host where you are signed in to Molly Roster. The Lab forwards only the `evaluate_molly_session` cookie to the local Evaluate API. `GET /api/stores` uses the account's authorized store scope. Employee identity, current formal job assignments, official CLOSED-round score and opening operation qualification come from the authenticated Evaluate roster integration API. `GET /api/store-jobs/{storeId}` shows the canonical job IDs to use for shift-pattern `role_code` values.

For a fresh local setup, run `scripts/provision_local_readonly.py` in the Lab virtual environment after a verified backup. It accepts only the loopback `molly_roster` target and creates an ignored `.env` with `ROSTER_DATABASE_READONLY_URL`; see the audit for scope and reversal. If the restricted URL is absent, Mock mode remains available but real-source reads fail before connecting to PostgreSQL; the launcher does not copy `backend/.env` credentials or pass through the legacy `ROSTER_DATABASE_URL`. The adapter uses parameterized SQL, `REPEATABLE READ READ ONLY`, a five-second statement timeout, and reads availability, shifts, assignments, period status, store settings and active shift templates. It treats the existing Prisma `timestamp without time zone` values as UTC clock values. No formal business table or migration is added. Deployments elsewhere must provision their own restricted account.

For a local before/after safety audit, run `.venv-isolated/Scripts/python.exe scripts/audit_roster_readonly_digest.py` from `scheduling-engine/` before and after the Lab solve. It uses the same restricted login and emits only row counts and SHA-256 content digests for the seven tables that login may read. It will reject a different database, role or writable transaction. Matching digests corroborate that those tables stayed unchanged during the experiment; the command does not inspect other tables or exclude simultaneous external edits.

`GET /api/source-preview/{storeId}?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD` checks the live source and returns counts/version without names. It also lists published or locked target shifts whose recorded positive break duration has no exact interval, with the source shift ID, start/end and assigned-person count. The response includes read-only store settings and active shortcut templates as review hints. The UI highlights published shift groups whose start/end/break duration do not match any active template. Settings, warning thresholds and templates never become Lab hard rules automatically. Missing or expired Evaluate sessions return HTTP 401, denied access returns 403, and source read failures return 503; there is no mock fallback. An account must have store access to read real data, save that store's Lab rules, or inspect its runs.

Preview and solve requests accept only inclusive date ranges of 1 to 14 days. Invalid or reversed ranges return HTTP 422 before loading a Roster snapshot or a Lab rules version.

For each previewed date, the Calendar compares the effective Lab opening and closing clocks with the Roster settings hint after applying weekday and date overrides. It also warns when Lab preparation starts after Roster's recorded opening, leaving that earlier interval outside the Lab demand timeline. These are review prompts, not an automatic rule override or proof that the Roster setting is current operating policy.

Mock store IDs cannot be used with the real data source. Calendar shift details and per-slot coverage display times in the saved run's store timezone.

The preview also aggregates already published assignments by local date, start/end, formal role and recorded break duration. This is a read-only reference for comparing a future candidate with current manual scheduling; observed historical shifts are not treated as a legal or operational rule.

For each observed published shift group, the preview reports the number of current store employees who both hold its formal job and submitted availability covering the entire shift, and how many of that pool have Evaluate's independent opening qualification. It separately shows the subset without any overlapping shift at another store. A second pool also requires the active Roster shift role's `requiredSkillCodes` to be present in Evaluate's `qualifiedSkillCodes`. It counts existing assignments whose current formal job or required skill is unconfirmed or whose submitted availability does not fully cover the shift. These are source-alignment checks only; the same person may appear in several shift groups, so group counts cannot be added. They do not subtract approved leave, minimum rest or applicable work and break policy, and missing availability may mean that a submission is incomplete. The preview response includes the resolved store timezone and `timezone_source`; the Lab uses that timezone when displaying these read-only references, independently of its unsaved rule example.

Historical Roster shift roles are associated with active Evaluate formal jobs by matching codes, plus the project's single approved `full-role`/`all-rounder` alias when both names are 全岗. Duplicate active Evaluate jobs with the same code stop the read instead of selecting an arbitrary job. Historical inactive Roster roles may still appear in fixed published shifts; an unmapped role remains unqualified input and causes a clear candidate configuration error.

For current scheduling eligibility, the Lab reads active Roster role `requiredSkillCodes` and checks them against each employee's Evaluate skill codes in candidate generation and independent replay. When multiple active Roster roles map to one formal job, exact formal-code matches take precedence over the legacy alias; within that match, the current store's role takes precedence over a global role. Malformed requirements or an equal-priority collision stop the source read. A preserved published or locked shift whose assigned employee lacks a currently required skill returns `LOCKED_QUALIFICATION` for review; the Lab does not silently legalize or replace that historical shift.

A real Lab run keeps its own aggregate published reference from the same source read in its saved result. The reference includes published shifts overlapping the requested local dates, including a previous-day shift continuing after midnight; comparison mode retains that preceding shift as fixed. The Calendar comparison groups reference and candidate headcounts by actual start/end instants, formal role and break duration; it does not substitute a later source preview for the run's historical reference. Local clock labels may repeat across a daylight-saving fall-back, so the comparison key uses UTC instants. Existing Roster data does not contain exact break timing, so the manual schedule's effective coverage during breaks cannot be stated precisely. The read-only reference and comparison views show pointwise conservative manual-headcount bounds between shift boundaries, including zero-staff gaps between observed shifts: the lower bound treats each untimed recorded break as potentially occurring in that span, while the upper bound assumes nobody is on break at that instant. These bounds do not assert a jointly attainable full-day break plan or prove demand coverage. The candidate's slot coverage remains independently validated.

For an independent candidate-versus-manual study on a date already published, choose **只读重排对比**. The `replace_target_published_for_comparison` solve option stores the original published shifts as the manual reference, then removes only that store's target-date `PUBLISHED` assignments from a detached in-memory snapshot before solving. Other-store shifts, other dates and `LOCKED` shifts remain constraints. The run records the mode, excluded assignment count and a distinct snapshot version. This is a hypothetical Lab comparison; it cannot be applied to the formal roster as-is. The default solve mode preserves published target shifts. Reviewed fixed-break overrides are rejected in comparison mode because those shifts are excluded from the candidate snapshot.

**Known source gaps:** Roster records only `breakMinutes`, not exact break intervals. Published or locked target shifts remain fixed. When their recorded break has no exact time, the solver places that break inside the matching shift pattern's permitted window and subtracts it from every affected coverage slot. Every fixed shift with a positive recorded break requires a matching pattern with the same total break duration and a confirmed paid/unpaid policy; an untimed break also needs a valid placement window. An exact manager-reviewed interval remains an optional API override through `fixed_break_intervals` with `source_shift_id`, timezone-aware `start` and `end`. Overrides are checked against the recorded duration and shift range, applied only to the in-memory snapshot, and never written back to Roster. Neither source has a verified approved-leave feed. A `REVIEWED` real solve rejects missing approved-leave, work/break-policy, or operating staffing-rule confirmation before loading the complete source snapshot, and rejects leave entries whose employee IDs are absent from that store snapshot. The UI accepts reviewed leave intervals as JSON objects with `employee_id`, ISO `start`, and ISO `end` with offsets; `[]` means no approved leave. Published target shifts use net minutes against the weekly cap when the configured pattern confirms an unpaid break. Existing shifts at other stores, whose paid status cannot be verified here, conservatively use gross minutes.

The 2026-10-26 Hurstville published 60-minute break has no decided start or end, as confirmed by the user. No exact interval needs to be entered for it. A candidate break placement is only an internal coverage assumption and must be displayed as uncertain. Real previews normally read the timezone from Roster store settings before interpreting local dates; the snapshot checks it inside the read-only repeatable-read transaction and again in a fresh read-only transaction before returning the snapshot. This detects changes during the snapshot read, although it cannot reserve future formal state. Saving real-store rules and running a real solve both reject a timezone that differs from the Roster setting. If a store has **no** Roster settings row, an operator may explicitly verify its IANA timezone and save a versioned Lab rule with `timezone_source=LAB_CONFIRMED`. A preview then uses that Lab value, labels its source, and both database reads confirm the formal row is still absent. An invalid formal row, a new formal row, or a conflicting rule stops the read and requires review. The Lab never infers this value from the store name or another store's rule; this option does not approve the business staffing rule or write formal Roster settings.

Published or locked target shifts must match an unambiguous configured complete pattern for their formal role, start/end instants and recorded break duration, including when the duration is zero. A known break interval must also fit that pattern's permitted window; it can disambiguate otherwise identical shift times with different break windows. An untimed break does not provide that evidence. A missing or still-ambiguous match returns a configuration diagnostic rather than declaring the preserved historical shift legal. Read-only manual references remain available for comparison even when the current rules do not match those shifts.

If a published or locked shift starts on the previous local date and continues into the requested work window, the Lab also requires the saved rule's validity range to cover that shift's start date. It will not apply a one-day rule retroactively to the preceding night's complete pattern or break policy. Such a run returns `FIXED_RULE_DATE_SCOPE` until a reviewed rule covers both dates; a read-only published reference can still be inspected without accepting a candidate.

Real source loading reads Evaluate employees and formal jobs both before and after the read-only Roster transaction. If their scheduling-relevant projection changes between those reads, the Lab reports a source-read error and requires a retry instead of combining two inconsistent source moments into one snapshot. This does not make the two systems one atomic database transaction; the run fingerprint records the observed input.
The read-only Roster shift query extends its surrounding window to cover the longest configured store or employee minimum rest period, with at least seven days of history for weekly work limits. Source preview and solve use the same saved rule to choose that window, so an external shift just outside the former fixed seven-day range cannot be silently missed.
The adapter also rejects duplicate active employee IDs or repeated source shift assignments, and the solver repeats those guards for any supplied snapshot before creating staffing variables.
The independent result validator compares every target-store published or locked shift overlapping the requested work window with the result's fixed shifts, including shifts that started on the previous date. It reports an omitted or invented fixed shift even in BEST_EFFORT mode, where staffing gaps themselves may be allowed.
Malformed Evaluate employee pagination or rows and invalid Roster shift rows are reported as source contract failures; the Lab does not substitute mock staff or shifts after a failed real read.

## Rules

Break durations must be divisible by the coverage slot size. Generated break candidates start and end on that grid, and a manager-reviewed exact interval must align precisely, including seconds, so coverage does not deduct an extra slot. `minimum_work_before_break_slots`, `minimum_work_after_break_slots`, and `minimum_work_between_breaks_slots` configure how many coverage slots of work must separate a break from the shift edges or another break. Zero removes that extra restriction. An older saved rule without these fields keeps the previous one-slot behavior, so its version does not silently change meaning. Rule saving now checks every configured start/end combination with the same break generator used for candidate shifts; a combination with no legal placement or more than 500 options returns a configuration error before a Lab rule version is written.

The complete-pattern editor exposes separate next-day switches for the earliest break start and latest break end. These switches set `break_rule.earliest_next_day` and `break_rule.latest_end_next_day` in the Lab rule draft; leaving them off keeps both times on the shift's start date. They do not assign a fixed break time to an untimed published shift.

Historical rules may contain numeric work/rest limits, but new API and CLI runs refuse them. New saves set `enforce_work_rest_limits: false` and clear employee limits. The engine continues to check availability, qualification, non-overlap and each pattern's recorded break duration. Real runs are exploratory and cannot pass the reviewed acceptance gate.

`base_day` retains shared shift pattern definitions. `weekly` maps Monday=0 through Sunday=6 to seven independent pattern-count maps. The Rules page selects one weekday at a time to set the minimum complete-shift count for each pattern. New saves require all seven days and clear `base_day.pattern_minimums`, `dates`, opening minima and time-slot demand. `STRICT` requires each count; `BEST_EFFORT` reports missing complete shifts by date and pattern. These are configurable minimums, not hardcoded Hurstville values. The engine still checks shift times, formal job qualification, employee availability, approved leave, overlap and each pattern's break count and duration. It does not constrain opening headcount, slot coverage or numeric work/rest limits for new runs. Historical rule versions retain their original values for audit.

Optional `valid_from` and `valid_through` fields restrict an entire saved rule version to an inclusive date range; both dates must be present together. The API rejects an out-of-range solve before loading the real source or saving a run, and the engine returns `RULE_DATE_SCOPE` when invoked directly. The Rules page exposes these fields and the Calendar shows the range. Use a single-day scope for a one-day exploratory rule so its `base_day` cannot be mistaken for approved rules on other weekdays. Copying a rule to another store preserves the restrictive range until the target store explicitly edits it.

Within a weekday or historical date override, `pattern_minimums` replaces the entire inherited map. An omitted pattern has a minimum of zero. New Lab rule versions record those implied zeros explicitly in the saved weekday configuration. The visual weekday editor retains the other displayed pattern counts when one count changes.

`employee_limits` is retained only for historical rule compatibility. New visual saves clear the map and disable numeric work/rest constraints. Employee identity for optimization preferences still comes from Evaluate.

`employee_preferences` is a separate optional map keyed by the same Evaluate employee ID. `desired_weekly_minutes` is a soft target, prorated to the selected number of days; when absent, the optimizer uses the source snapshot's desired minutes if available, otherwise an equal-share target. `hourly_cost_cents` is a Lab-only modeled hourly cost. The current real Evaluate integration does not provide either field. When the labor-cost weight is positive, every employee with a generated candidate must have a cost value; otherwise the run returns `CONFIG_ERROR/MISSING_LABOR_COST` instead of treating unknown costs as zero. The Rules page can edit these values, and cross-store copying clears them. Lab preferences are not written to Evaluate or formal Roster data.

The Rules page can load another store's saved rule version as an **unsaved draft** for the selected store. It copies shift patterns, weekday counts and optimization settings; date, opening, demand and employee limit overrides are cleared on save. The target timezone is retained, but timezone authority resets to `ROSTER` and must be separately verified for the target. A saved copy records its source store/version in `copied_from`. Review the target store's formal role IDs before saving. The target store's normal validation rejects unknown formal roles. Loading a draft does not modify either store's saved rules.

Switching stores loads that store's saved rules and discards unsaved local drafts. The Calendar blocks a solve while the displayed rule has unsaved changes. It sends the displayed rule version with the solve request; the API returns HTTP 409 if that version is no longer current, before creating a run.

For a real solve, first check the current source for the selected store and full date range. The Calendar sends the reviewed saved rule version as `expected_rule_version` and that preview's `snapshot_version` as `expected_source_version`; both are mandatory for `REAL`. It clears the preview and the separate leave, policy and staffing-rule confirmations when their review scope changes. A late response from an older store, date, view or data-source selection is ignored. The API re-reads the source before solving: a missing version returns HTTP 422, while a changed rule or source version returns HTTP 409 without saving a run. Review the current rule and source, then repeat the manual confirmations before retrying.

For a local real-data engine experiment with **simulated** Lab rules, select “探索性模拟” and “只读重排对比” together. `run_purpose=EXPLORATORY` still requires an authorized store, a saved Lab rule, the current rule and source versions, and a fresh read-only source load. It always excludes target-date published assignments from a detached comparison copy; other-store, other-date and locked assignments remain constraints. Approved leave, work/break policy and operating staffing rules may remain unconfirmed, so the result and history are permanently labelled exploratory, `acceptance_gate=NOT_ELIGIBLE`. Its `OPTIMAL` or `FEASIBLE` status and independent validation mean only that the supplied simulated model was solved and replayed; they do **not** establish a legal or operationally usable roster. Unreviewed leave intervals cannot be submitted as if the leave list were complete. The reviewed real-run path requires all three distinct manual confirmations. Neither path writes a shift to formal Roster.

The engine's direct `solve` entry point enforces the same three confirmations for `REAL`/`REVIEWED` snapshots, independently of the HTTP precheck. A snapshot explicitly records whether published target shifts were preserved or detached for comparison. Every real result records the review state and comparison mode; `MANUAL_REVIEW_REQUIRED` requires a complete, gap-free STRICT result with all three confirmations and preserved published shifts. Exploratory, failed, gap-bearing and detached comparison results are `NOT_ELIGIBLE`, including direct engine calls. The Lab API repeats the comparison gate after solving as a second boundary. Any future formal apply endpoint must reject comparison mode independently, including historical runs with an older gate label.

The direct solver also rejects approved-leave entries that reference employees absent from the source snapshot, matching the HTTP route. Manually supplied exact break intervals are normalized to UTC before snapshot fingerprinting, so equivalent instants written with different time-zone offsets produce the same snapshot version.

The real-source adapter reads all Roster availability statuses. `AVAILABLE` intervals form the positive windows; explicit timed `UNAVAILABLE` intervals are subtracted so a candidate cannot cross one, matching the formal Roster's overlap veto. `UNKNOWN` creates no positive availability. Source fingerprints include these status rows, so changing an unavailable interval makes an old preview stale. An `AVAILABLE` row without both instants, or a partly timed `UNAVAILABLE` row, is a source-contract error rather than silently incomplete availability. A wholly untimed `UNAVAILABLE` row creates no interval veto, matching the current Roster validator.

Time windows, recorded break intervals and manually supplied exact breaks use UTC instants at the engine boundary. This preserves their actual order and overlap across a daylight-saving fall-back hour, even if local clock labels repeat. The daylight-saving correction began with engine version `0.1.1`, rule-boundary validation uses `0.1.2`, break-aware draft stability uses `0.1.3`, the restricted-connection requirement uses `0.1.4`, next-day demand starts use `0.1.5`, and unknown rule/request field rejection uses `0.1.6`. Saved runs retain the engine version that produced them. Demand segments outside a day's complete preparation-to-work-end window are rejected rather than silently clipped. For a segment starting after midnight in an overnight work day, set `start_next_day: true`; set `end_next_day: true` when its end is also on the next calendar day. These flags are available in the base, weekday, and date demand editors. Rule saves and solve requests reject misspelled or otherwise unknown fields with HTTP 422 instead of silently ignoring them.

The authenticated Hurstville 2026-10-26 exploratory runs and all of their simulated assumptions are recorded in [docs/hurstville-exploratory-2026-10-26.md](docs/hurstville-exploratory-2026-10-26.md). The current date-scoped `hurstville:v3` rule is a Lab experiment, not the store's accepted rule.

Each `ShiftPattern` has a canonical formal role ID, allowed full-shift starts and ends, and a break rule. A break rule specifies 0–2 breaks, duration, allowed window, paid/unpaid status and the optional minimum work slots around breaks. The solver selects employee, whole shift and break option together. A break removes an employee from effective staffing even when paid. The default objective penalizes excess coverage and unnecessary work first, then uses fairness, score, preferred patterns, late-start preference and draft stability as configurable soft weights; optional hourly cost belongs to the earlier efficiency tier. Draft stability rewards only a matching employee, role, full shift and recorded break duration; if an exact draft break interval exists, the selected break option must match it. The independent validator replays every selected interval and returns `DATA_ERROR` on a mismatch.

The template displayed for a real store is marked `UNSAVED_EXAMPLE_REPLACE_RULES`. It is **not** a statement of that store's real staffing demand or role definition. Replace all sample hours, demand, patterns and `role_code` IDs before saving a real store's rules.

The fairness objective counts already fixed work whose shift starts fall within the selected date range, including other-store assignments, alongside new candidate work. It does not try to equalize only the newly generated shifts while ignoring existing commitments.

Optimization is layered. All legal and qualification constraints remain hard. `BEST_EFFORT` minimizes staffing gaps first; both modes then minimize excess coverage, unnecessary work and configured labor cost when those weights are nonzero. Fairness, score, preferred patterns, late starts and draft stability are optimized within the best earlier-tier bound found. A proven optimum is fixed exactly; an unproven feasible incumbent gives the later tier a no-worse bound. The previous tier's complete solution is passed as a hint to the next tier, which helps week-scale runs reach preference optimization without relaxing the earlier bound. Weights remain adjustable within their tier, so a large skill weight cannot buy an avoidable extra shift while efficiency is enabled. If any tier is unproven, the run stays `FEASIBLE` and records `priority_proven=0`; `objective_stage` names the last solved tier. `objective_score` is that stage's value and should only be compared within the same stage and rule version. An official score of zero is distinct from a missing score.

## API

- `GET /api/health` (engine version and formal-write flag), `/api/stores`, `/api/store-jobs/{storeId}`, `/api/employee-rule-targets/{storeId}`
- `GET|POST /api/rules/{storeId}` — store-scoped versioned Lab configuration; the UI sends `X-Expected-Rule-Version` (`__NONE__` for the first save) so a stale editor gets HTTP 409 instead of overwriting a newer rule
- `GET /api/rules/{storeId}/versions/{version}` — read one saved historical rule version under the same store authorization
- `GET /api/source-preview/{storeId}?start_date=...&end_date=...` — authenticated, read-only source check
- `POST /api/solve` — `{store_id,start_date,end_date,expected_rule_version?,expected_source_version?,mode,source,run_purpose,leave_data_complete,compliance_policy_confirmed,staffing_rules_confirmed,approved_leave,fixed_break_intervals,replace_target_published_for_comparison}`; both expected versions are required for `REAL` and must match the saved rule and latest preview. `EXPLORATORY` requires `REAL` and read-only replacement comparison; default `REVIEWED` requires separate leave, work/break-policy and operating staffing-rule confirmations.
- `GET /api/runs/{storeId}`, `/api/run/{runId}`, `/api/run/{runId}/rules` — local run history and its exact saved rule configuration. The Calendar's read-only “查看本次规则” panel uses the run-scoped endpoint; a later rule edit cannot change the historical response.

There is no formal Roster write endpoint. Future integration must use an authenticated, versioned Roster API with explicit user review, rather than direct writes to `shifts` or shared Evaluate tables. See [phase-progress.md](docs/phase-progress.md) for verified phase status, [hurstville-pilot-rule-review.md](docs/hurstville-pilot-rule-review.md) for the outstanding real-store inputs, and [integration-readiness.md](docs/integration-readiness.md) for the future interface boundary.
