# Candidate-to-Roster integration preparation

The Lab endpoint returns `RunResult` with a stable `run_id`, `engine_version`, `snapshot_version`, `rule_version`, full start/end instants, proposed break placements, role IDs, per-slot coverage and validation errors. `break_time_inferred=true` marks a fixed published shift whose source recorded a break duration but no time; its returned interval is a simulation choice and is not a confirmed historical fact. It never writes an official shift.

The Lab's `REPLACE_TARGET_PUBLISHED` comparison mode deliberately omits target-date published assignments only from an in-memory candidate snapshot while preserving the original manual reference. Its output is hypothetical and must never be treated as directly applicable to an already published roster. A future reviewed apply API must re-read the authoritative roster, handle publication and change control explicitly, and must not accept this comparison-mode run as an automatic write request.

Before a formal integration is enabled, the Roster backend needs a review and apply endpoint that:

1. Re-fetches the same store's current Evaluate workforce and Roster availability/shift versions under the requesting account's authorization.
2. Rejects stale snapshot/rule versions, conflicting published or edited shifts, any `run_purpose=EXPLORATORY` or `acceptance_gate=NOT_ELIGIBLE` result, and any `comparison_mode=REPLACE_TARGET_PUBLISHED` result even if an older Lab version assigned it a different gate.
3. Requires manager review of the proposed full shifts, break durations and allowed windows, plus leave and compliance confirmation. An exact break interval is optional when operations leave it undetermined.
4. Maps canonical Evaluate formal job IDs to active Roster shift role IDs through the existing explicit association logic; do not match by display names or skills alone.
5. Validates availability, qualifications, cross-store overlap, rest, weekly cap and coverage again on the server.
6. Retains the formal Roster's break duration even when no interval is set. Effective headcount for such a published shift must be shown as a range or as an explicitly labeled scenario. If exact break intervals are added later, keep them optional, retain existing `breakMinutes` for backward compatibility, and migrate only after a schema and user-data audit.
7. Applies a selected candidate as a draft in one version-checked transaction with idempotency, audit actor and rollback strategy. Publishing remains a separate manager action.

Approved leave and applicable employment-policy data require an authoritative source or an explicit, audited manual attestation. The current source schemas do not provide those facts. No formal schema migration, direct DB write, Calendar button or publishing-flow change is part of this Lab.

Formal Roster checks cross-store time overlap against assignments in both draft and published periods during create/update and publish. The Lab reads both states and treats an other-store draft as an external shift for overlap, minimum-rest and work-cap checks. A future apply endpoint must repeat that all-status check under its write transaction; a Lab candidate does not reserve another store's draft.

The current Evaluate integration also has no authoritative employee desired hours or hourly cost. The Lab can version optional per-employee weekly desired minutes and modeled hourly costs without changing Evaluate; a positive labor-cost weight requires costs for every candidate employee. A future formal integration must either retain this clearly labeled manager-maintained model or obtain a separately authorized cost source and apply its access controls. Do not interpret Lab costs as payroll facts.

The current daily and weekly net-work caps assign a complete cross-midnight shift to its local start date and that date's Monday week. This accounting basis must be reviewed against the store's applicable policy before a real candidate is accepted; it is not a claim about a legal calendar-day rule.
