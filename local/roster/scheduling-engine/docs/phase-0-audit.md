# Phase 0: current model and safety review

Examined the existing React/Vite frontend, Express/Prisma Roster backend, Roster PostgreSQL schema and Evaluate Molly Prisma schema/API before adding the Lab. No current `/scheduling-engine/` existed. No existing Roster page, API or table was modified for this Lab.

| Source | Relevant data | Ownership and use |
|---|---|---|
| Evaluate Molly | Store, Employee, StoreJobDefinition, EmployeeJobAssignment, latest valid CLOSED official score, opening operation skill | Canonical identity, formal job grants, score and qualified skills; read via authenticated `/api/roster-integration` and `/api/store-jobs` |
| Molly Roster | `roster_periods`, `shifts`, `shift_assignments`, `employee_availability`, `shift_roles`, `roster_store_settings` | Availability and existing all-store shift conflicts; read via parameterized PostgreSQL transaction |
| Lab SQLite | `rule_versions`, `runs` | Separate local rule history and candidate run artifacts only |

The Roster tables use quoted camelCase columns despite snake-case table names. `startAt` and `endAt` are stored as UTC clock values in PostgreSQL `timestamp without time zone`. Availability statuses are `AVAILABLE`, `UNAVAILABLE`, `UNKNOWN`: only explicit `AVAILABLE` intervals become candidate availability. `UNAVAILABLE` is not proof of an approved leave request. `shifts.breakMinutes` cannot identify when an employee was off duty. Neither source schema has a verified approved-leave table. A fresh read-only `information_schema.tables` query against both running PostgreSQL databases on 2026-10-25 found no table whose name contains `leave`, `absence`, `timeoff`, or `time_off`; source-code and Prisma-schema searches likewise found no approved-leave contract. Those missing inputs are surfaced rather than invented.

Risk boundaries: real store reads require an Evaluate session and authorized store; a failed source read does not fall back to mock; all Lab records remain outside formal Roster PostgreSQL; the source connection starts `REPEATABLE READ READ ONLY`; formal publishing and editing remain unchanged. The first local run fell back to the backend's writable database login. A later local security change created and verified a dedicated SELECT-only role for the Lab after a backup; see [roster-readonly-connection.md](roster-readonly-connection.md). Any other deployment must establish its own restricted login. A local SQLite file containing real run output is sensitive staff scheduling data.

The currently running Roster backend has data: the Phase 0 check observed 9 role records, 28 shifts, 66 assignments and 96 availability rows. A browser-authenticated Hurstville source preview for 2026-10-26 read 25 active employees, 22 relevant availability windows and 41 existing assignment rows within the surrounding rest/week window. This proves both the Evaluate and Roster read paths, but does not constitute a completed real candidate schedule: leave and policy attestations are still missing.

A fresh read-only Hurstville settings/template check on 2026-10-25 found stored opening/closing values of 09:00/22:00, `minimumShiftMinutes=30`, `defaultBreakMinutes=0`, and weekly/daily **warning** thresholds of 38/10 hours. Active convenience templates were AA 10:00–22:00 with 60 minutes' break, BB 10:00–17:00 with 30 minutes' break, and CC 16:00–22:00 with no break. These are existing UI settings/templates, not an approved staffing demand or applicable work/break policy: the 2026-10-26 published reference contains 10:00–17:00 shifts with zero recorded break and 17:00–22:00 shifts, so template contents cannot simply be promoted into hard optimizer rules. The warning thresholds are not legal maximums. The Lab leaves actual permitted patterns, demand and paid/unpaid break policy for manager review.

## Schema and migration decision

The current Roster Prisma schema declares a compound `[rosterPeriodId, storeId]` foreign key from Shift to RosterPeriod, a ShiftRole reference with restricted deletion, a unique `(shiftId, employeeId)` ShiftAssignment key, and indexes on store/date for Shift and EmployeeAvailability. Evaluate's canonical schema indexes Employee by store/status and has store-scoped StoreJobDefinition and EmployeeJobAssignment records. The Lab reads those authorities and stores no duplicate employee master records.

No formal PostgreSQL migration is needed for the isolated Lab. Its only new tables are `rule_versions` and `runs` in a separate local SQLite file under `.data`; initialization uses `CREATE TABLE IF NOT EXISTS`. Rollback is to stop the Lab and remove **only that isolated SQLite file after backing it up**, leaving both production databases untouched. A future formal integration would need a separately reviewed migration for exact rest intervals and versioned draft application, first tested against a disposable database. That migration is outside this development phase.
