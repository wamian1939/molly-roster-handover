# 智能体规则与日历写入

当前操作入口为主系统的左侧“智能体规则” (`/agent-rules`) 和日历工具栏“智能体排班”。原 `/multi-agent` 地址重定向到日历并展开排班面板，不再要求在独立班表页面导出／导入结果。

## 使用流程

1. 选择门店、排班周，设置每天连续时段的精确人数。首时段人数就是开早人数，包含 Full，没有额外开早人数相加。
2. 规则可保存为“固定规则，每周重复”或“临时规则，仅选定周”。临时规则按周一日期定位，到下一周使用固定模板；保存保留版本并检查并发修改。
3. 在日历中选择日期，展开“智能体排班”，点击“开始智能体排班”。程序自动读取最新规则和真实报班，重新安排所选周；不需要先读取输入或勾选确认。
4. 验证后的结果直接显示在当前 `/calendar` 的原时间轴中，色块内用小字“智能体排班”标注来源，不进入独立结果页面或候选切换模式。
5. Node 后端继续跟踪任务，结束后保存通过独立人员／时间／工时校验的班次。已知人手不足的日期也继续由 Daily Agent 选人，不再跳过整天；同日修复仍不能排满时，保留尝试中实际覆盖需求最多的合法组合，提交工时台账后继续下一天。全周不完整时以 `PARTIAL_DRAFT` 保存这些班次，并保留明确的缺口状态。关闭面板不会取消已启动的后台任务。
6. 日历只显示真实 `shifts`／`shift_assignments` 记录，全部进入同一个普通编辑、删除窗口，不再把只读候选叠在真实日历上。写入前重新读取规则、员工和报班并检查日历版本；来源已变化或事务失败时不写入。修改时间、换人、删除继续使用普通日历的 Availability、岗位、重叠与版本检查。

## 日历候选与任务进度

- 默认只显示运行状态、已处理天数、进度条和耗时。五阶段、每日班次与工时、修复情况和失败原因放在“运行详情”中。日期处理完毕不等于验证成功；实际保存数量以事务回执为准。
- 主日历不消费 `calendar_preview`，不再存在智能体专用只读详情。引擎保留此字段供独立诊断与验证使用；普通日历只有保存后的真实班次，色块仅用小字标注来源。未排满日期的合法班次也会保存，和人工班次一样可编辑删除。JSON 中 `incomplete_dates` 与 `failed_days[].coverage` 明确记录不足日期和每个半小时的需／实人数；`calendar` 包含已排出的草稿，整体 `validation.valid=false`、`publishable=false`，不会伪装完整成功。
- 进度区默认直接展示各未完全满足日期的已排班次数和缺口，例如“11:00–16:00 缺 1 人（需要 4，已排 3）”，相同连续时段合并显示，不必先展开详情。
- 从侧边栏进入普通 `/calendar` 时，进度区默认展开，按当前登录与门店从服务端恢复最近日历任务，不依赖 `agent=1` 参数或浏览器缓存。即使任务属于另一周，也立即显示其实际日期范围和进度，并提供对应周班表定位；不自动改变当前日历日期，不会自动发起新的模型请求。服务端恢复不会覆盖用户刚在当前页面启动的新任务。
- 真实任务 `64ea3f55-3210-4b89-bf83-65c29ffdc1c7`（2026-10-26 至 11-01）结果为 FAILED：4 天、34 个候选班次通过当日独立重放，周三／周六来源容量缺口，周四同日修复耗尽。仅生成本地预览证据，没有把这一不完整星期写入真实班表；未改变任务原始结果或放宽人数规则。

## 数据与边界

- Python 引擎仍只生成、验证候选，不直接写正式班次；写入通过 Roster 后端、现有 Evaluate 登录及门店权限完成。
- 使用正式 CLOSED 评分、唯一 Availability、正式岗位和现有班次接口；不引入另一套员工或评分数据库。评分工时比例与 Bob 固定晚班条件保留，公平性权重为 0。
- 人数设置保存在引擎独立的 `.data/agent-rule-settings.sqlite3`，按门店、固定／指定周和版本分开保存，不修改 CP-SAT 的已保存规则。生效 RuleSet 在来源版本中标明 agent 配置版本。
- 覆盖按 30 分钟、半开区间 `[start,end)` 精确检查，Full 只计一次完整班次和工时。不支持跨日回溯、自动休息或额外优化求解器。
- `best_effort` 只允许在明确标记日期保留未满足需求；人数上限、员工存在性、Availability、资格、重叠、工时上限和锁定班次检查不变。原始 RuleSet 人数不改。比较的是 LLM 在修复预算内提出的合法组合覆盖量；不声称数学全局最优，不引入求解器。
- 写入前重新验证真实输入及当前员工岗位；事务内继续检查 Availability、重叠、门店和周期、班次版本。
- 日历来源摘要在发起生成前捕获，事务加门店锁后再次比较。人工编辑、新增、删除或周期变化会拒绝覆盖。
- 对待替换的原始日历保存服务端审计备份，默认位于 Roster backend 的 `.data/agent-calendar-audit/<run-id>.json`；可通过 `MULTI_AGENT_AUDIT_DIR` 指定安全持久化目录。备份不包含 API Key 或登录 Cookie。
- 生成班次使用任务和候选 ID 导出的稳定 UUID，复用现有 `shift_create_requests` 做写入回执。重试不会重复添加班次，也不会撤销写入之后的人工编辑。没有新增正式数据库表或迁移。
- 班次记录写明“智能体排班／班型／休息尚未安排”。`breakMinutes=0` 表示本引擎尚未安排休息，不代表员工无需休息或工资工时已确认。

## 本地验证

新增测试覆盖规则版本、指定周覆盖、来源权限、未验证日期不得写入、后台保存、普通日历刷新与编辑删除、原班表备份、原子回滚、生成期间人工编辑保护、写入重试后保留人工修改，以及首次创建日历周期。

测试写入仅使用迁移后的隔离 PostgreSQL schema，测试员工未用于实际门店排班。当前真实门店班次没有因为开发验收被覆盖。运行中的主系统和引擎需要分别验证 HTTP 健康；这些检查和组件／数据库测试不替代真实登录后的浏览器端到端验收。

本轮验证结果：Python 引擎 70 项通过；后端 36 个文件、311 项数据库测试通过；前端排除此前已有 4 项失败的模板页后，64 个文件、531 项通过。主应用构建、前后端 TypeScript 和变更文件 ESLint 通过。一次全并发运行的旧 500 行复制用例超过默认 5 秒，降低并发后在干净隔离 schema 上全量重跑通过，没有修改该用例或业务逻辑来绕过失败。

本地 `/agent-rules`、`/calendar?agent=1` 及两个后端健康接口响应正常；真实来源规则请求也已在引擎日志中返回 200。没有代替用户登录或发起本次真实门店排班覆盖。正式表与早期审计基线已有变化，本轮没有回滚这些现有变化，也没有把旧基线当作正式表仍未变化的证据。
