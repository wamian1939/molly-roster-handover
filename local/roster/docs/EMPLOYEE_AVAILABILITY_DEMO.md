# 员工个人报班演示

本地入口：`http://127.0.0.1:5176/employee/availability`。
个人入口在该地址后加 `?account=demo-1`、`?account=demo-2` 或 `?account=demo-3`。
三个账号是 Hurstville 演示员工，不对应真实员工。选择账号后只返回该账号自己的报班记录。

## 当前行为

- 按周每天直接选择门店代码（当前 Hurstville 为 AA 10:00–22:00、BB 10:00–17:00、CC 16:00–22:00）、无法报班或未填写。一天只能选择一个代码。
- 整周输入支持 `1AA 2BB 3CC`、`1aa2bb3cc`、`1-5AA`，不填写员工姓名。服务器使用现有 `parsePresetTimeSlotScript` 解析，按当前登录模拟账号绑定身份；重复星期、未知代码及夹带其他姓名全部拒绝。预览不写入，核对后再提交。
- 代码和时间只读读取 Roster 中已保存的 `AvailabilityScriptShortcuts`，不另建映射。配置与容量规则一起纳入提交版本校验，提交时再次解析并验证代码与时段一致。当前演示支持门店同日、半小时精度的代码。
- 提交后可修改，服务重启后演示报班记录保留。默认打开门店下一周。
- 每半小时对照现有精确人数规则计算报班覆盖。同一账号只计一次，连续时段可合并覆盖；仅相交但未完整覆盖的时段不计入该半小时。
- 绿色：人数低于需求；黄色：达到需求但不足需求的 120%；红色：达到或超过需求的 120%。需求为零时红色。红色不限制提交。
- 员工接口仅返回颜色、时间，不返回需求数、已报数或他人报班。相邻同色时段合并显示。
- 规则直接只读读取 `scheduling-engine/.data/lab.sqlite3` 里的最新基础规则，以及 `multi-agent-engine/.data/agent-rule-settings.sqlite3` 里的周临时或固定规则。临时规则优先；规则缺失或需要复核时显示错误。
- 演示容量只计入三个模拟账号的报班，尚未读取正式员工报班。页面明确标示演示状态。
- 防止同一账号多页面覆盖；账号切换、记录版本或规则变化会要求重新核对；后台容量更新保留未提交草稿。

## 存储与范围

新增接口位于 `/api/employee-demo`，仅开发模式注册。前端入口也仅开发模式启用。
模拟登录用独立 HttpOnly 会话 Cookie，与管理端的 Evaluate 会话分开。
无需修改 Prisma 模型或迁移。演示报班保存至忽略的 `backend/.data/employee-demo-reports.json`，通过写入队列与原子替换保存。
不修改正式 `employee_availability`、班次或发布记录。现有规则数据库通过 SQLite `mode=ro` 读取。

## 正式接入仍需完成

1. 接上正式员工账号认证和 canonical Evaluate Employee ID 绑定，依据在职状态和门店执行服务端权限。
2. 将个人报班接入 Roster Availability，保留已有版本校验、已排班冲突和跨日规则；只按有效在职员工的报班统计容量。
3. 用现有规则服务替换本地只读桥接，继续沿用临时规则优先和规则版本验证。
4. 确定报班开放周期、截止时间、跨日填写和员工公网可访问的部署地址，再上线正式入口。

演示个人链接只是账号选择入口，不是正式身份凭证。当前本机地址不能作为员工远程使用的正式链接。
