**当前交互已更新：** 左侧为“智能体规则”，在日历工具栏发起排班并将验证通过的结果直接写入普通日历。原独立主应用入口已重定向到日历。当前操作与写入边界见 [智能体规则与日历写入](AGENT_RULES_AND_CALENDAR_WRITE.md)；下文保留此前接入、只读验收和语义修正记录。

主应用左侧新增“智能体排班”，路由 `/multi-agent`。页面复用登录会话、门店选择、正式员工接口和 CP-SAT 的竖版 `ScheduleViews` 组件；没有新增员工、评分或数据库表。

## 使用

正常启动 `scripts/start-dev.ps1` 后打开 `http://127.0.0.1:5176/multi-agent`。该脚本会在 4191 未启动时启动独立 Python 引擎；可用 `-SkipMultiAgent` 跳过。Evaluate 服务和数据库仍须可用。远程部署应配置 Roster 后端的 `MULTI_AGENT_ENGINE_URL`，并单独部署 Python 引擎及其只读数据源、模型配置，本次没有执行远程发布。

选择门店和周一，读取真实输入，确认规则版本、员工数、报班摘要、正式 CLOSED 评分和既有班次处理方式，然后生成候选。默认“重新生成独立草稿”，仅在内存候选中分离当前门店目标日期的可编辑班次，无论数据库旧字段为 DRAFT 还是 PUBLISHED。只有来源明确标记 LOCKED 的记录、其他门店和其他日期班次继续保留，不从发布状态推断锁定。也可明确选择“保留已有班次并补齐”，表示本次生成沿用这些班次，不代表日历中的班次不可编辑。没有删除或覆写数据库班次。

Hurstville 使用已确认的基础 RuleSet 和 `multi-agent-engine/configs/hurstville-business-v1.json` 的评分比例、Bob 周二/周四晚班规则。评分公平性权重保持 0。不具备已确认规则的门店显示错误，不使用示例员工或其他门店规则代替。

页面展示四个 Agent 进度、每天验证提交后的工时版本、竖版班表、逐时段覆盖、员工目标工时与实际工时。运行任务绑定登录会话和门店；刷新页面可恢复，服务重启后可读取该会话已落盘结果，未完成任务标为中断。只有整周验证通过并再次通过独立重放的草稿可导出 JSON。导出仍为 Draft，休息、工资工时与正式发布不由本入口自动处理。

“查看最近真实测试结果”按当前账户门店权限读取已保存的真实测试，并重放其硬约束验证，不使用浏览器公开 capability token。当前保存的 Hurstville 结果为 2026-10-26 至 2026-11-01，周三和周六失败，不会宣称整周成功。

## 接入边界和验证

浏览器只访问 `/api/multi-agent/*`。Express 先检查 Evaluate 登录和门店权限，再转发允许的具体路径；仅转发 `evaluate_molly_session` Cookie，不开放匿名样例、任意路径或浏览器自定义 Policy。引擎再次验证门店与运行会话。API Key 保留在 Python 服务配置中。

验证：引擎 61 项测试通过，后端新接口/基础/原有排班路由 105 项通过，新增页面 5 项通过；前后端 TypeScript、前端构建和变更文件 ESLint 通过。正式 Roster 健康检查 database=true、evaluateMolly=true，主页面 HTTP 200，引擎配置已就绪。两个后端的真实入口均拒绝匿名读取（401）。只读审计的 7 张正式 Roster 表内容摘要与接入前基线一致。

浏览器自动检查被运行环境中止，原因是无法可靠识别 Windows 浏览器当前 URL。本次没有完成真实登录会话下的端到端页面验收；接口权限和组件行为使用隔离测试验证，不能替代真实门店账号验收。没有正式班表写入、数据库迁移或远程部署。

## 接入端口修正

原端口 4190 属于 Fetch 禁止端口。Python 独立健康检查可以通过，但 Node 20 的实际 fetch 会直接以 `bad port` 失败，导致主系统返回“智能体排班服务暂时无法连接”。单独服务健康正常和 mock-fetch 单元测试不足以证明后端到引擎已连接。

默认端口、启动脚本、环境示例及 Lab 导航现已统一改为 4191。运行中的后端已重新加载新默认地址，引擎已重启。使用真实 Node fetch 验证 `/multi-api/health` 返回 200，配置已就绪；真实数据接口未带会话时返回 401，说明请求已到达引擎登录检查。真实用户登录后的完整操作仍需在页面验收。

## 输入诊断语义修正

实际重读 2026-10-26 至 2026-11-01 的数据库后，复现原提示 24、24、23、2、1。周一、周二的 24 项全部为 `FIXED_EXACT_EXCESS`，是旧班表在 24 个半小时时段超过精确人数要求，并非 24 名员工没有资格。周四的 2 项也是旧班表人数超额。原页面用“人员、资格或固定班次冲突”统一描述且直接累加时段，造成误解。

新页面明确选择生成模式，默认独立草稿；以半开区间合并同一原因、同一人数和同一员工集合的连续时段，分别显示保留班次超额、实际候选不足、同日多时段容量不足及指定员工限制。每条保留原始逐槽诊断供 Validator 使用；已经用单时段不足解释的约束不再重复输出联合容量提示。可用人选不足时展示要求人数、报班可用人数、合法候选人数与姓名。

实时只读证据位于 `multi-agent-engine/.data/diagnostic-preserve-20261101T125917/`，含原始 Snapshot、RuleSet、来源及两种模式的诊断。分离 41 条目标周已发布班次后，周一、周二、周四不再有输入冲突；周三 11:00–16:00 需求 4 人，当前报班覆盖且满足合法候选条件的为 HandoverEmployee015、HandoverEmployee014、HandoverEmployee007 共 3 人。周六 11:00 和 17:00 合计需求 13 人次覆盖，每日一个完整班次及当前 Full 资格下的候选容量上界为 11。结论仅对应当前数据库报班、岗位和 RuleSet，不能替代对实际员工情况的人工核对。

诊断修复回归：引擎 64 项、页面 6 项通过；主应用构建通过。原 CP-SAT 和正式班表未修改。

## 当前日历可编辑语义

用户明确当前日历的班次可点击修改或删除，业务没有“发布后锁定”的步骤。引擎已改用独立的 `multi_agent/working_snapshot.py`，不再借用只分离 PUBLISHED 的 CP-SAT 对照适配器；CLI、诊断脚本及主系统接入使用同一规则。新接口的 `detached_existing_count` 统计本次候选中另排的已有班次，`scheduling_mode` 明确本次是重排还是沿用。评分、Availability、岗位、精确覆盖及逐日状态验证保持有效。

回归验证引擎 66 项、页面 6 项通过，新增混合 DRAFT/PUBLISHED、跨店/跨日期、显式锁定记录保留和新候选不重复计算工时的场景。原 CP-SAT 代码和当前数据库班次没有修改。

审计发现主日历 `CalendarPage.editShift/openGroup` 和后端 `RosterService` 存在按 PUBLISHED 拒绝编辑/删除的旧逻辑。用户随后明确确认“一起修正主日历和引擎：已有班次可直接编辑、删除”，现已移除此限制。

## 主日历直接编辑与删除
