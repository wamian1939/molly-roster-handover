- 正式评分：直接调用 Evaluate 的 `RosterIntegrationService`，继续复用最新有效 CLOSED 轮次汇总逻辑。
- Evaluate 查询在 RepeatableRead + READ ONLY 事务中执行；Roster 继续使用原只读连接和原 Availability 否决逻辑。
- 使用当前已保存 Hurstville v20 精确人数规则。41 条已发布目标周班次仅在内存中分离，数据库原班次未改动。
- `fairness_weight=0`、`preference_weight=0`，不做平均工时分配，不为了工时低而替换员工；工时台账仍准确记录。

合计 **43 个已接受班次，其中 5 个 Full**。通过日期共有 120 个半小时时段，均满足精确覆盖。失败日期不放入未经验证的候选班次，因此全周状态保持 FAILED，不能导出为“全周通过”的正式草稿。

周三 11:00–16:00 每半小时需要 4 人，但现有合格且可用员工最多只有 3 人。周六 11:00 与 17:00 两个时段合计需要 13 人次覆盖；在允许 Full 覆盖两段、每人每日一个完整班次的条件下，现有候选最多提供 11 人次覆盖。后者是必要容量上界证明，不是把早晚人数误当成互斥员工数量。

Daily Agent 在实测中曾混淆相似员工 ID、漏算人数。当前模式改为由同一个 Daily LLM Agent 每次选择一个仍合法的候选班次，确定性代码只过滤违法追加并反馈实时缺口，不选择员工、不搜索排班组合、不调用 CP-SAT。每一天仍在完整验证通过后才提交一次；失败日不更新台账，后续日期可继续生成诊断班表。模型在周六进行了同日尝试后失败，该记录保留；独立双时段容量上界已补充到可视化诊断中，后续运行可提前识别。

界面直接复用 CP-SAT Lab 的 `ScheduleViews`，默认全周竖版，也可切换单日、点击员工班次查看时间和原因、查看每半小时 Coverage。根地址 `http://127.0.0.1:4190/` 自动打开本次真实结果，不再默认显示合成员工样例。结果查看是本机只读记录，不改变既有生产 API 的登录与写入权限。

另有同一日历组件静态导出的 `real-roster-vertical.html`，服务未启动时也能打开。静态渲染核对了 7 天、43 个班次元素、实际员工姓名，并确认没有 synthetic/Test employee 内容。

证据位于忽略目录 `.data/live-real-no-fairness-v3/`：`provenance.json`、`snapshot-original.json`、`snapshot-scheduling.json`、`rules.json`、`events.jsonl`、`result.json`、`real-roster-vertical.html`。四个 LLM Agent 均实际调用；最终 Audit 也指出周三、周六是已知失败日，拒绝跨日重排，全周结果未伪装为成功。
